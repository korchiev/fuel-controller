# RS-485 lab

Этот каталог проверяет физический путь между двумя USB-RS485 адаптерами. Учебный протокол колонки и `SerialTransport` здесь пока не участвуют.

Сейчас готовы Phase 1–8. Кадр собирает `build_frame` из `src`. По проводу его возит `SerialTransport`. Он не знает, что такое AUTHORIZE. Несколько колонок на одном порту обслуживает `VirtualTransport.deliver()`: кадр видят все, отвечает только свой адрес.

## Что доказывает Phase 2

Один байт проходит так:

```
Python → COM-порт → USB-RS485 #1 → витая пара A/B → USB-RS485 #2 → второй COM-порт → второй Python
```

`0x41` — это число 65. В ASCII это буква `A`. Программа отправляет один бинарный байт, а не текст `"41"`.

## Железо и проводка

Два USB-RS485 адаптера в одном компьютере. Связь двухпроводная, half-duplex.

```
Adapter #1 A    <------>  Adapter #2 A
Adapter #1 B    <------>  Adapter #2 B
Adapter #1 GND  <------>  Adapter #2 GND
```

`+5V` не подключать.

На коротком лабораторном кабеле терминаторы 120 Ом не стоят.

## Зависимость

Скрипты запускает Windows Python. Процесс внутри WSL эти COM-порты не видит.

```powershell
py -3.13 -m pip install pyserial
```

## Phase 1 — список портов

```powershell
cd \\wsl.localhost\Ubuntu-22.04\home\vsamato\fuel-controller
py -3.13 lab\list_ports.py
```

Скрипт не выбирает адаптер сам. На этой машине адаптеры — `USB-SERIAL CH340` на `COM5` и `COM6`. `COM3` и `COM4` — Bluetooth, их не открывать.

## Phase 2 — один байт

Сначала приёмник, потом отправитель. Байт, отправленный раньше, уже потерян: шина его не хранит.

Два окна PowerShell. В первом:

```powershell
py -3.13 lab\receiver.py COM5
```

Во втором, после строки `Waiting for bytes`:

```powershell
py -3.13 lab\sender.py COM6
```

Порты можно поменять местами. Скорость, биты, чётность и стоп-бит должны совпадать. Сейчас это 9600, 8, NONE, 1. Это лабораторная настройка, не настройка Tatsuno.

Ожидаемый вывод отправителя:

```
Transmitted: 1 byte
hex: 41
decimal: 65
ASCII: A
```

Ожидаемый вывод приёмника:

```
Received:
hex: 41
decimal: 65
ASCII: A
```

Остановить приёмник: Ctrl+C.

## Phase 3 — шесть сырых байт

`--frame` берёт байты из уже написанного протокола: `build_frame(2, AUTHORIZE, 50)`. Это те же шесть чисел `02 02 20 32 54 03`, не текстовая строка `"02 02 20 32 54 03"`.

Приёмник ещё не разбирает кадр. Он ждёт, пока после байтов наступит тишина длиной в timeout (1 секунда), и печатает группу через `data.hex(" ")`. Пауза перед строкой — это ожидание тишины, а не дополнительный `sleep`.

Сначала приёмник:

```powershell
py -3.13 lab\receiver.py COM5 --burst
```

Затем отправитель:

```powershell
py -3.13 lab\sender.py COM6 --frame
```

Ожидаемый вывод с обеих сторон:

```
02 02 20 32 54 03
```

У отправителя перед этим будет `Transmitted: 6 bytes`. У приёмника — `Received 6 bytes:`.

## Phase 4 — запрос и ответ

Два процесса. Оба используют код из `src`.

Устройство — `VirtualPump` на одном адаптере. Оно читает 6 байт через `SerialTransport` и отвечает тем кадром, который колонка уже умеет строить. Для AUTHORIZE на 50 литров из состояния IDLE это `02 02 06 01 09 03`: ACK и состояние AUTHORIZED.

Контроллер — `VirtualPumpDriver` на другом адаптере. Драйвер собирает кадр. `SerialTransport.exchange()` только записывает байты и читает 6 байт ответа.

Сначала устройство:

```powershell
py -3.13 lab\device_simulator.py COM5
```

Затем контроллер:

```powershell
py -3.13 lab\controller_test.py COM6
```

Ожидаемый журнал контроллера:

```
TX [6 bytes]: 02 02 20 32 54 03
RX [6 bytes]: 02 02 06 01 09 03
accepted = True  state = AUTHORIZED
```

`DATA=1` в ответе — это состояние AUTHORIZED, не налив. Пока окно колонки не закрыто, она помнит этот шаг. Дальше, не перезапуская её:

```powershell
py -3.13 lab\controller_test.py COM6 --command start
py -3.13 lab\controller_test.py COM6 --command stop
py -3.13 lab\controller_test.py COM6 --command reset
```

Цепочка: IDLE → AUTHORIZED → FUELING → FINISHED → IDLE. Повторный `authorize`, пока колонка не в IDLE, получает NAK, и состояние не меняется. `status` состояние только читает.

Настройки с обеих сторон должны совпадать. По умолчанию 9600, 8 бит, чётность `N`, 1 стоп-бит, timeout 1 секунда. Для опыта 8E1 у обоих процессов добавить `--parity E`.

Ошибки не сваливаются в одно исключение:

- `TIMEOUT` — за timeout не пришло ни одного байта.
- `INCOMPLETE RESPONSE` — байты пришли, но меньше шести.
- `INVALID FRAME` — шесть байт есть, но кадр или контрольная сумма не сходятся. Это решает `parse_frame`, не транспорт.

Паузы между запросом и ответом нет. Контроллер уже ждёт внутри `read()`, и одной секунды хватает на разворот half-duplex.

## Phase 5 — опрос нескольких адресов

Один процесс на COM5 держит несколько колонок. Контроллер на COM6 по кругу шлёт `GET_STATUS`: адрес 1, затем 2, затем 3. `GET_STATUS` состояние не меняет.

Колонки живут только пока открыто окно симулятора. Закрой старый симулятор, если он ещё слушает COM5, и запусти его с тремя адресами:

```powershell
py -3.13 lab\device_simulator.py COM5 --addresses 1,2,3
```

Во втором окне:

```powershell
py -3.13 lab\poll_controller.py COM6 --addresses 1,2,3
```

Ожидаемая строка на каждую колонку, между журналами TX/RX:

```
pump 1: ACK IDLE
pump 2: ACK IDLE
pump 3: ACK IDLE
```

Адрес, которого на COM5 нет, молчит. Опрос повторяет его 3 раза и затем печатает `OFFLINE`. Остановить опрос: Ctrl+C.

`--interval 0.5` — пауза после каждого опроса, чтобы журнал можно было читать. Шине она не нужна. Следующий кадр и так уходит только после ответа или после timeout.

Пока опрос остановлен, прежнее окно симулятора можно подвинуть одной командой, например разрешить только колонку 2:

```powershell
py -3.13 lab\controller_test.py COM6 --command authorize --address 2 --liters 30
```

Потом снова запустить опрос. Колонки 1 и 3 останутся IDLE, колонка 2 будет AUTHORIZED. Оба процесса нельзя одновременно открывать на COM6.

## Phase 6 — сбои и повторы

Опрос отличает четыре исхода:

- `ACK` — колонка ответила и приняла запрос. Повтор не нужен.
- `NAK` — колонка ответила и отказала. Повтор того же кадра не нужен.
- `TIMEOUT`, `INCOMPLETE RESPONSE`, `BAD CHECKSUM` — достоверного ответа нет. Запрос повторяется.
- `OFFLINE` — все попытки этого круга не дали ACK или NAK. Следующий круг начинает сначала.

По умолчанию попыток три, `--retries 3`. Для каждого опыта закрой старый симулятор и подними его с одним `--fault`. Во втором окне опрашивай один адрес и один круг, чтобы не ждать лишнее.

Тишина, ответа нет:

```powershell
py -3.13 lab\device_simulator.py COM5 --addresses 1 --fault silence
py -3.13 lab\poll_controller.py COM6 --addresses 1 --scans 1 --interval 0
```

Три строки `TIMEOUT`, затем `OFFLINE`. На это уходит около трёх секунд: каждая попытка ждёт timeout.

NAK, колонка жива и отказала. Состояние на симуляторе не меняется, повтор один:

```powershell
py -3.13 lab\device_simulator.py COM5 --addresses 1 --fault nak
py -3.13 lab\poll_controller.py COM6 --addresses 1 --scans 1 --interval 0
```

Ожидается `pump 1: NAK IDLE`.

Битая контрольная сумма. Шесть байт приходят, `parse_frame` их отвергает, опрос повторяет:

```powershell
py -3.13 lab\device_simulator.py COM5 --addresses 1 --fault bad-checksum
py -3.13 lab\poll_controller.py COM6 --addresses 1 --scans 1 --interval 0
```

Три строки `BAD CHECKSUM`, затем `OFFLINE`.

Короткий ответ, два байта вместо шести:

```powershell
py -3.13 lab\device_simulator.py COM5 --addresses 1 --fault short
py -3.13 lab\poll_controller.py COM6 --addresses 1 --scans 1 --interval 0
```

Каждая попытка — `INCOMPLETE RESPONSE`, потому что `read` дожидается шести байт и не дожидается.

Задержка меньше timeout всё ещё заканчивается ACK. Задержка больше timeout становится `TIMEOUT`. Ответ, пришедший уже после отказа контроллера, следующий запрос сбрасывает, если он успел лечь в буфер порта до новой передачи:

```powershell
py -3.13 lab\device_simulator.py COM5 --addresses 1 --fault delay --fault-delay 0.3
py -3.13 lab\poll_controller.py COM6 --addresses 1 --scans 1 --interval 0
```

Настоящий NAK без флага: колонка в IDLE, команда STOP ей не подходит.

```powershell
py -3.13 lab\device_simulator.py COM5
py -3.13 lab\controller_test.py COM6 --command stop
```

## Phase 7 — налив и транзакция

Пресет больше не просто записанное число. После `start` симулятор сам прибавляет целые литры, по умолчанию 5 литров в секунду. Кадр по-прежнему шестибайтовый, поэтому по проводу едут целые литры, не `1.2`. Сумма считается только в окне симулятора: отпущено, умноженное на `--price` (по умолчанию 2). В кадре суммы нет.

Закрой старый симулятор и запусти:

```powershell
py -3.13 lab\device_simulator.py COM5 --address 2 --flow 5 --price 2
```

Во втором окне, по очереди:

```powershell
py -3.13 lab\controller_test.py COM6 --command authorize --liters 20
py -3.13 lab\controller_test.py COM6 --command start
```

Окно колонки само печатает ход налива, примерно каждые секунду, пока ждёт следующий кадр:

```text
pump 2 FUELING  delivered = 5 / 20 L  amount = 10.00
pump 2 FUELING  delivered = 10 / 20 L  amount = 20.00
pump 2 FINISHED delivered = 20 / 20 L  amount = 40.00
```

Когда счётчик дошёл до 20, колонка сама перешла в FINISHED. Снять объём:

```powershell
py -3.13 lab\controller_test.py COM6 --command transaction
```

`DATA` в ответе — это литры, не номер состояния. Ожидается `volume = 20 L`.

`stop` до конца пресета оставляет уже отпущенное. Например, остановить на 10 литрах и сразу спросить транзакцию: `volume = 10 L`. `reset` после этого возвращает IDLE и обнуляет счётчик. Последний пресет по-прежнему остаётся 20.

`--flow 0` останавливает счётчик: колонка стоит в FUELING, пока не придёт `stop`.

## Phase 8 — контроллер отдельно от протокола

Команды, которые ты уже запускаешь, теперь проходят через `ForecourtController`. Он знает номер колонки и литры. Шесть байт кадра собирает `EducationalDriver`. В журнале перед обменом есть строка `driver = EducationalDriver`.

`TatsunoDriver` стоит в том же слоте. Вызов `authorize` у него останавливается с `NotImplementedError`: протокол колонки ещё не записан, транспорт под него уже есть.

Тот же порядок на кабеле, что и в Phase 7. Закрой старый симулятор, если он запущен до этого кода, и подними его снова.

## Если байт не дошёл

- Неверный COM-порт. Снова запустить `list_ports.py` и открывать только строки `USB-SERIAL CH340`.
- Порт уже открыт другим окном или программой. Закрыть лишний `receiver.py` / `sender.py`.
- Разная скорость, чётность или стоп-бит. Оба процесса должны быть 9600 8N1.
- A и B перепутаны. Имена A/B у разных плат не совпадают. Поменять A и B на одном адаптере и повторить опыт. Программа сама полярность не исправляет.
- Нет общего GND. Для этого опыта земля адаптеров соединена.
- Приёмник запущен после отправителя. Байт уже ушёл.
- Драйвер CH340 не создал COM-порт. Тогда адаптера нет и в `list_ports.py`.
